# 협업을 위한 개발 가이드 (교육안)

- 일시: 2026-06-30
- 대상: 프론트엔드/백엔드 개발자
- 목적: 팀 내 개발 방식 통일과 AI 기반 협업 생산성 향상

## 1. 프로젝트 구조 간단 설명 (프론트, 백엔드)

### 프론트엔드

- 위치: `frontend/src/`
- 최상위 폴더 구조

  ```
  src/
  ├── app/          앱 진입점, 라우팅, 전역 Provider 설정
  ├── pages/        화면 단위 기능 (역할별 하위 폴더로 구분)
  ├── services/     API 통신 및 백엔드 응답 정규화
  ├── shared/       공통 컴포넌트, 훅, 상수, 유틸, 상태
  ├── mocks/        MSW 기반 테스트 핸들러
  └── test/         통합 테스트 (앱 셸, 페이지 단위)
  ```

- **pages 폴더 – 메뉴 기준 분리 (목표 구조)**

  현재 코드는 `admin/`, `platform-admin/`, `tenant-management/` 세 폴더에 분산되어 있어 메뉴 단위로 찾기 어렵다.
  아래 구조를 기준으로 정리해 나간다.

  ```
  pages/
  ├── auth/                         로그인, 도메인 인증
  │
  ├── platform-admin/               1. 플랫폼 관리 (플랫폼 관리자 전용)
  │   ├── plans/                      ㄴ 플랜 관리
  │   ├── tenants/                    ㄴ 업체 관리
  │   ├── menus/                      ㄴ 메뉴 관리
  │   └── login-history/              ㄴ 로그인 이력 관리  ← 현재: admin/LoginHistoryPage.tsx
  │
  ├── organization/                 2. 조직 관리
  │   ├── users/                      ㄴ 사용자 관리      ← 현재: tenant-management/users/
  │   └── authorities/                ㄴ 권한 관리        ← 현재: platform-admin/authorities+roles/
  │
  └── documents/                    3. 문서 관리
      ├── list/                       ㄴ 문서 목록        ← 현재: tenant-management/documents/
      └── history/                    ㄴ 문서 이력
  ```

  > **현재 분산 현황** (정리 전)
  >
  > - `pages/admin/LoginHistoryPage.tsx` → platform-admin/login-history/ 로 이동 필요
  > - `pages/platform-admin/roles/`, `authorities/` → organization/authorities/ 로 통합 필요
  > - `pages/tenant-management/users/` → organization/users/ 로 이동 필요
  > - `pages/tenant-management/documents/` → documents/ 로 이동 필요

  ▶ **페이지 단위 컴포넌트 분리 규칙** (플랜 관리 예시)

  ```
  pages/platform-admin/plans/
  ├── PlatformPlanManagementPage.tsx  ← 페이지 컴포넌트 (쿼리/상태 조율)
  └── components/
      ├── PlatformPlanSearchBar.tsx   ← 검색 조건 UI
      ├── PlatformPlanGrid.tsx        ← 목록 테이블
      ├── PlanMenuMappingDialog.tsx   ← 메뉴 매핑 팝업
      └── PlanFeatureMappingDialog.tsx ← 기능 매핑 팝업
  ```

  - 페이지 컴포넌트: 데이터 패칭(useQuery), 상태 조율, 하위 컴포넌트 연결
  - `components/` 하위: 검색바, 그리드, 다이얼로그 등 UI 단위로 1파일 1역할
  - 다이얼로그는 열림 여부와 선택된 데이터만 props로 받아 독립적으로 동작

- **services 폴더 – API 계층**
  - `services/api/apiClient.ts`: axios 인스턴스, 토큰 인터셉터 공통 처리
  - `services/plan/planAccessService.ts`: 플랜 목록, 메뉴 코드, 기능 조회/저장 API + 응답 타입 정의
  - `services/platform/`: 메뉴, 권한, 테넌트 등 플랫폼 관련 API 묶음
  - `services/auth/`: 로그인, 로그아웃, 토큰 처리

  ▶ 규칙: 컴포넌트는 서비스 함수를 직접 호출하지 않고 **React Query(`useQuery`/`useMutation`)** 를 통해서만 호출

- **shared 폴더 – 재사용 자원**
  - `shared/components/`: 화면에서 공통으로 사용하는 UI 조각
    - `layout/`: `PageHeader`, `AdminGrid` 등 레이아웃 컴포넌트
    - `data/`: 테이블, 페이징 등 데이터 표시용 컴포넌트
    - `feedback/`: 알림, 스낵바 등
    - `forms/`: 공통 입력 컴포넌트
  - `shared/hooks/`: `useFeedback` (성공/실패 알림), `useGridPagination` (페이지 상태)
  - `shared/store/`: Zustand 전역 상태 (인증 정보, 권한 등)
  - `shared/constants/`: `labels.ts` 등 화면 텍스트 상수

- **개발 흐름 예시 (플랜 관리 기준)**
  1. `planAccessService.ts` 에서 API 함수와 타입 정의
  2. `PlatformPlanManagementPage.tsx` 에서 `useQuery`로 데이터 가져오고 필터/선택 상태 관리
  3. `PlatformPlanSearchBar`, `PlatformPlanGrid` 에 props로 내려주는 방식으로 UI 분리
  4. Dialog 컴포넌트는 열림 상태와 선택 플랜만 받아 독립적으로 동작

### 백엔드

- 위치: `backend/`
- 핵심 구조
  - `src/main/java`: 도메인/서비스/컨트롤러 구현
  - `src/main/resources`: 설정 및 매퍼/리소스
  - `src/test/java`: 단위/통합 테스트
  - `DATABASE`: 스키마, 마이그레이션, 시드, 운영 스크립트
- 개발 포인트
  - 계층 분리(Controller-Service-DAO) 준수
  - SQL/매퍼 변경 시 스키마 및 마이그레이션 문서 동기화

## 2. 프론트, 백엔드 개발 패턴 통일

### 공통 원칙

- 네이밍 규칙 통일: 기능 기준 명명 + 일관된 suffix 사용
- 계층 책임 분리: 화면/요청 처리/비즈니스/데이터 접근 역할 명확화
- 에러 처리 표준화: 사용자 메시지, 로그 포맷, 예외 매핑 규칙 통일
- 테스트 기준 통일: 최소 단위 테스트 + 핵심 플로우 통합 테스트 확보

### 프론트 패턴

- API 호출은 `services`를 통해서만 수행
- UI 컴포넌트는 표현 로직 중심, 비즈니스 로직은 훅/서비스로 분리
- 공통 타입을 기준으로 요청/응답 모델 표준화

### 백엔드 패턴

- Controller: 입력 검증/응답 포맷
- Service: 트랜잭션 및 비즈니스 규칙
- DAO/Mapper: 데이터 조회/저장 책임 한정
- DB 변경은 SQL + 문서 + 실행 스크립트까지 한 세트로 관리

## 3. superpowers 스킬을 이용한 AI 개발

### 왜 쓰는가

- 작업 접근 방식(브레인스토밍, 디버깅, 계획 수립)을 표준화
- 코드 변경 전 요구사항 정리와 검증 절차를 강제
- 팀원 간 AI 활용 편차를 줄이고 산출물 품질을 일정하게 유지

### 기본 사용 흐름

1. 작업 요청 수신
2. 관련 스킬 선택 (`brainstorming`, `writing-plans`, `verification-before-completion` 등)
3. 설계/계획 문서화
4. 구현 및 검증
5. 리뷰 및 반영

### 실무 적용 팁

- 단순 수정도 최소한의 설계 의도를 먼저 합의
- "완료" 선언 전 테스트/검증 로그를 반드시 확인
- 공통 프롬프트 템플릿과 스킬 사용 예시를 팀 문서로 축적

## 4. 공통된 작업지시서를 가지고 시연

### 시연 시나리오 (예시)

- 주제: "메뉴 관리 기능에 필드 1개 추가 및 목록/상세 반영"
- 목표: 같은 작업지시서를 바탕으로 프론트/백엔드/DB 변경을 일관되게 수행

### 작업지시서 템플릿

- 배경/목적
- 요구사항 (필수/선택)
- 영향 범위 (프론트/백엔드/DB)
- API/데이터 계약 변경 사항
- 테스트 케이스
- 완료 조건(Definition of Done)

### 시연 순서

1. 작업지시서 확인 및 질의
2. AI 스킬 기반 계획 수립
3. 프론트/백엔드 병행 구현
4. 테스트 실행 및 결과 확인
5. 리뷰 포인트 정리
