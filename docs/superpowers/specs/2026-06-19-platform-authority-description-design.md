# 플랫폼 권한 설명 저장 및 표시 정합성 개선

## 배경

플랫폼 권한 관리 화면에서 권한 수정 시 설명 입력값이 수정 후 유지되지 않는다. 프론트엔드는 설명 필드를 요청 payload에 포함하고 있지만, 백엔드 권한 API와 `tb_authorityinfo` 스키마에는 설명 저장 경로가 없다. 또한 권한 목록 그리드 헤더는 실제 데이터 의미와 다르게 `내용`으로 표시되고 있다.

## 문제 요약

- 권한 수정 모달의 설명 값이 저장되지 않는다.
- 권한 목록 재조회 시 설명이 항상 비어 있거나 기본값으로 보인다.
- 권한 목록 그리드 헤더가 `설명`이 아니라 `내용`으로 표시된다.

## 목표

- 권한 설명을 `tb_authorityinfo`의 정식 저장 필드로 추가한다.
- 권한 등록, 수정, 목록 조회에서 설명이 일관되게 round-trip 되도록 맞춘다.
- 권한 목록 그리드 헤더를 `설명`으로 변경한다.
- 프론트 테스트와 최소 백엔드 검증으로 회귀를 막는다.

## 비목표

- 권한 테이블의 기존 레벨, 상태, 정책 로직 변경
- 권한/메뉴 매핑 기능 구조 변경
- 다른 관리 화면의 공통 라벨 체계 전면 수정

## 설계

### 1. 데이터 모델

`tb_authorityinfo`에 권한 설명 컬럼을 추가한다.

- PostgreSQL 로컬 스키마 파일에 설명 컬럼을 추가한다.
- 컬럼명은 기존 네이밍과 맞춰 `authority_dc`를 사용한다.
- 기존 데이터와의 호환성을 위해 nullable 컬럼으로 둔다.

이 선택의 이유는 현재 권한 엔티티가 `authority_code`, `authority_nm` 중심의 명명 규칙을 따르고 있고, 메뉴 테이블도 설명에 `menu_dc`를 사용하고 있어 일관성이 가장 높기 때문이다.

### 2. 백엔드 API

`AuthorityInfoVO`에 설명 필드를 추가하고, 플랫폼 권한 API의 조회/등록/수정 경로가 모두 이 필드를 통과하도록 맞춘다.

- `AuthorityInfoVO`에 `authorityDc` 필드를 추가한다.
- `/api/platform-admin/roles` 조회 SQL에서 `authority_dc AS authorityDc`를 select 한다.
- 권한 등록 SQL에서 `authority_dc`를 insert 한다.
- 권한 수정 SQL에서 `authority_dc`를 update 한다.
- 등록/수정 API는 기존처럼 `AuthorityInfoVO`를 그대로 반환하므로, 응답에도 설명이 포함된다.

상태 변경 API는 설명을 변경하지 않으므로 기존 동작을 유지한다.

### 3. 프론트엔드 정규화

프론트는 외부 API 변형을 흡수하기 위해 현재의 `description` 필드 기반 UI 모델을 유지한다.

- `platformRoleService`의 API 타입에 `authorityDc?: string`을 추가한다.
- 목록/등록/수정 응답 정규화 시 `description ?? authorityDc ?? ''` 순서로 설명을 읽는다.
- 등록/수정 요청은 기존 `description`과 함께 `authorityDc`도 같이 보낸다.

이렇게 하면 백엔드가 정식 필드명으로 응답해도 UI 모델은 바꾸지 않아도 된다.

### 4. 화면 표시

권한 목록 그리드의 세 번째 컬럼 헤더를 `설명`으로 표시한다.

- 권한 관리 화면에서 `APP_LABELS.field.content` 대신 고정 텍스트 `설명`을 사용한다.

이 변경은 다른 화면의 `내용` 라벨 사용처를 건드리지 않고, 현재 권한 목록의 의미만 정확히 맞춘다.

### 5. 테스트 전략

프론트에서 실패 테스트를 먼저 보강한다.

- 수정 모달 저장 시 설명 값이 `updatePlatformRole` payload에 포함되는지 검증한다.
- 권한 목록 헤더에 `설명`이 렌더링되는지 검증한다.
- 서비스 정규화가 `authorityDc` 응답도 처리하는지 검증한다.

백엔드는 최소 검증으로 다음을 확인한다.

- VO 필드 추가 후 컴파일이 깨지지 않는지 확인한다.
- 가능하면 관련 테스트 또는 모듈 단위 컴파일을 수행한다.

## 구현 순서

1. 프론트 테스트에 실패 케이스를 추가한다.
2. 프론트 권한 목록 헤더와 서비스 정규화를 수정한다.
3. 백엔드 VO와 MyBatis SQL을 수정한다.
4. 로컬 PostgreSQL 스키마 파일을 갱신한다.
5. 프론트 테스트와 백엔드 검증을 실행한다.

## 리스크 및 대응

- 실제 운영 DB에 컬럼이 없으면 신규 백엔드 배포만으로는 동작하지 않는다.
  - 대응: 이번 변경은 로컬/문서 기준 스키마를 먼저 맞추고, 운영 반영 시 동일 컬럼 추가 마이그레이션이 필요하다고 명시한다.
- 기존 응답이 `description` 또는 `authorityDc` 중 어느 이름으로 오더라도 혼용될 수 있다.
  - 대응: 프론트 정규화에서 두 필드를 모두 허용한다.
- MSSQL과 PostgreSQL 매퍼가 다르면 한쪽만 수정될 수 있다.
  - 대응: 두 매퍼 파일을 함께 수정한다.

## 완료 기준

- 권한 등록/수정 후 설명이 재조회 시 유지된다.
- 권한 목록 그리드 헤더가 `설명`으로 표시된다.
- 프론트 관련 테스트가 통과한다.
- 백엔드 관련 컴파일 또는 테스트 검증이 통과한다.

## 운영 반영 메모

- 애플리케이션 배포 전 `tb_authorityinfo.authority_dc` 컬럼 추가가 선행되어야 한다.
- PostgreSQL과 MSSQL 모두 동일한 설명 컬럼을 맞춰야 프론트 round-trip 이 보장된다.
